# 代码地图

按一条文档走过的顺序列文件、函数和表。先读 1–4，测试（`tests/`）不用读。

## 1. 文档进来：`pull/`

- `service.py` 的 `run_forever` 按 `atlas_settings` 的间隔/暂停/立即跑循环，每轮 `run_round` 对白名单里启用的来源调 `fabric.py` 的 `pull_source`；SIGTERM 干净退出。
- `pull_source` 翻 `GET /api/fabric/changes`，每页再取 `clean-text?quality=true`，`filter_page` 过两道关（`allowed_by_whitelist`、`allowed_by_quality`），用 `map_document` 变成 `documents` 的字段。
- `store.py` 的 `save_page` 一页一个事务：写 `documents`（按 `document_uuid(来源, 记录号)` 一行）和 `fabric_pull_state`（序号、最新序号、跳过数）。
- 管理接口 `api/routers/pull.py`（口令 `api/admin_auth.py`）：白名单、质量门槛、状态、暂停/恢复/立即跑、按需请求 `request_versions`。
- 表：`documents`（本地缓存，`fabric_version_id` 记版本）、`fabric_pull_state`、`atlas_pull_whitelist`、`atlas_settings`、`atlas_admin_log`。

## 2. 抽取：`flows/`

- 入口：`api/routers/extraction.py` 的 `/trigger`、`/trigger/pending`、`/re-extract/{uuid}` → `flows/extraction_flow.py` 的 `run_extraction_for_uuids` / `run_extraction_batch`，把 uuid 交给队列。
- 队列：`flows/extraction_worker.py`（memory：线程；redis：RQ 队列 `extraction`，作业函数 `flows/extraction_rq_job.py` 的 `extraction_job`）；`core_engine/task_queue.py` 管暂停标志和队列读数，读不到就明确报错，不当成 0。
- 一篇文档：`extract_single_document`
  1. `flows/chunking.py` 的 `split_document` 分块（表格块单独切）；
  2. `flows/extraction_prompts.py` 的 `get_extraction_prompt` 按来源组 prompt，`core_engine/cloud_api_client.py` 的 `qwen_extract_structured` 调模型；
  3. `_parse_chunk_output` 按 `flows/entity_schemas.py`（实体类型）和 `VALID_RELATION_TYPES`（关系类型）白名单校验，`_model_data` 去掉模型给的下划线键；
  4. `_merge_chunks` 跨块去重、重排关系下标；
  5. 消歧（下一节）；
  6. 全局写锁后 `db/repository.py` 的 `insert_extraction_result` 一个事务写 `extracted_entities`、`entity_relations`，更新 `documents.extraction_status`（`pending → queued → processing → done / failed / no_entity`）。
- 实体类型和判定标准见第 9 节；字段定义在 `flows/entity_schemas.py`，抽取规则和 few-shot 在 `flows/extraction_prompts.py`。

## 3. 消歧：`disambiguation/`

`engine.py` 的 `disambiguate_entities` 对每个实体调 `disambiguate`：

| 步 | 在哪 | 结果 |
|---|---|---|
| 1 强 ID | `rules.py` 的 `match_strong_id`（`STRONG_ID_FIELDS`：股票代码、CAS、靶点基因、试验号、批准文号、通路 ID） | 命中就直接链接 `dict_id` |
| 2 别名 | `db/repository.py` 的 `lookup_alias`（先用 `normalizer.py` + `normalization_rules.py` 规范化名字，盐型、公司后缀等） | 命中就直接链接 |
| 3 类型规则 | `rules.py` 的 `match_by_entity_rules`（Company / Drug / Target） | 候选 |
| 4 向量召回 | `search_similar_entities`（pgvector 余弦，带 `is_verified`） | 候选集 |
| 5 精排 | `llm_ranker.py` 的 `rank_with_reranker`（BGE Reranker；返回不合法当失败）；`rank_with_llm` 备用 | 候选 / 模糊 / 新实体 |
| 6 路由 | `routing.py` 的 `route_decision`：按置信度分级，已核实（`is_verified`）的才能自动链接 | 自动 / 人工 / 新实体 |

消歧过程写在 `entity_data["_disambig"]`，审核页面用它显示候选。

## 4. 审核：`api/routers/review.py` + `db/repository.py`

- 实体：`approve_entity_with_alias_writeback`（合并 `canonical_data`、回写别名和 embedding、按 `dict_id` 去重）、`reject_entity`、批量接口；同一 `dict_id` 第二次命中自动置 `auto_approved`。
- 关系：`approve_relation`、`reject_relation`、批量接口。
- 字段冲突：多来源字段不同进 `entity_merge_queue`，`resolve_merge` / `batch_resolve_merges` 裁决（只处理未解决的、锁行）。
- 身份合并：`merge_entities`（写 `entity_merge_log` 前后快照）、`rollback_merge`；Agent 提的合并进 `entity_identity_merge_proposal`，人确认。
- 计数：`db/review_listeners.py` 监听审核状态变化，`db/review_lifecycle.py` 的 `recalc_document_state` 重算 `documents.pending_entity_count / total_entity_count`。
- 日志：`review_log`（审核前后）、`operation_log`（写操作）。

## 5. Agent：`core_engine/agent_runner.py` + `core_engine/agents/`

`get_agent_runner()` 是唯一入口，接口在 `api/routers/agent.py`：

| Agent | 文件 | 做法 |
|---|---|---|
| 实体审核 | `agents/entity_review.py` | 三步：有效性 → 类型 → 原文依据 |
| 关系审核 | `agents/relation_review.py` | 三步：端点 → 类型 → 原文依据 |
| 冲突裁决 | `agents/conflict_resolver.py` | ReAct，结果 keep_existing / accept_new / custom |
| 语义匹配 | `agents/semantic_matcher.py` | 两个字典实体是不是同一个 |
| 合并消歧 | `agents/entity_merge.py` | 把抽出的实体链到字典，SSE 推送推理过程 |

工具在 `core_engine/agent_tools/`（查库、联网搜索、类型规则、提交决策），提示词 `agents/prompts.py`，阈值和来源权威度 `agent_config.py`。
每次运行写 `agent_run`（`db/agent_run_repo.py`），前端 `ReasoningTimeline` 显示步骤。

## 6. 同步到 WeKnora 的 Neo4j：`core_engine/weknora_graph_client.py`

接口 `api/routers/weknora.py` 的 `/graph/*`：先 `entity_dict` 镜像，再实体，再关系，可分步或 `/graph/sync-all`。
状态在 `entity_dict.weknora_sync_status` 和 `extracted_entities / entity_relations.weknora_graph_status`（`pending / pushed / failed`）。
同一个实体用字典 id 当幂等键，重复同步只更新。

## 7. 页面：`frontend/src/`

`router/index.ts` 列了全部页面：总览 `PipelineOverview`、文档 `DocumentList / DocumentDetail`、单篇审核 `ReviewWorkbench`、
批量审核 `BatchReviewWorkbench`、图谱审核 `GraphReview`、实体合并 `EntityMerge / MergeWorkbench`、字段冲突 `FieldConflict`、
身份合并提案 `IdentityMergeProposals`、Agent `AutoReviewDashboard / DocumentReview`、`Neo4jManager`、`WeknoraManager`。接口封装在 `src/api/`。

## 8. 表和迁移

`db/models.py` 是表结构，`migration/versions/V0xx__*.sql` 是建表和改表（`migration/migrate.py` 按版本号执行一次）；`db/schema.sql` 是早期的一份全表 SQL，只作参考。

表：`documents`、`fabric_pull_state`、`atlas_pull_whitelist`、`atlas_settings`、`atlas_admin_log`、`entity_dict`、`entity_aliases`、`extracted_entities`、`entity_relations`、`review_log`、
`operation_log`、`entity_merge_queue`、`entity_merge_log`、`entity_identity_merge_proposal`、`agent_run`、`schema_migrations`。
约定：软删除（`is_deleted`）、不用外键，关联由 `repository.py` 的事务保证。

## 已知的坑

- 交叉验证自动通过（第二次命中同一 `dict_id` 就 `auto_approved`）没有置信度门槛，可能放过误合并。
- 向量召回要有效的 Embedding 密钥，没有时只剩第 1–3 步在起作用。
- `memory` 队列重启丢任务；正式跑用 `redis` + `rq worker extraction`。
- CORS 现在允许 `*`，对外开放前要收紧。

## 9. 实体类型和判定标准

16 类，抽取、审核、消歧共用这一套（字段在 `flows/entity_schemas.py`）。

| 大类 | 类型 | 命名锚点 |
|---|---|---|
| 实体型：身份稳定，要跨文档对齐，是消歧主对象 | Company（受监管的经营/机构实体）、Drug、Target、Indication、Pathway、Compound（中药活性成分/化学单体）、TCMFormula（方剂/饮片） | 完整官方名、INN 通用名、HGNC 符号、ICD/MeSH 名、通路标准名 |
| 事件/实例型：每次都是新实例，天然 new_entity | ApprovalEvent、SafetyEvent、RecallEvent、DealEvent、Policy、ClinicalTrial、DevelopmentProject | 主体 + 事件类型；ClinicalTrial 用 NCT/CTR 注册号，没号时用试验代号或整句标题 |
| 附属型：挂在别的实体上 | DealItem（挂 DealEvent，HAS_ITEM）、TrialIndication（挂 ClinicalTrial，EVALUATES，`注册号-适应症-分期`） | — |

总原则：类型表达「它是什么」，不表达「它在什么语境里」。同一本体在哪都是同一类型（疾病不论是适应症还是不良反应语境都是 Indication），语境用关系表达（`TREATS`、`CAUSES`）。

要点：

- **Company**：独立法人不合并（母子公司各自成实体）；品牌/集团简称归母公司；内设机构独立于母机构。
- **Indication**：只收疾病本体。症状、体征、检验异常（MedDRA PT，如 QT 延长）不成实体，并入安全事件的「事件内容」段。「X 引起的 Y」：同一 X 对应 ≥2 个 Y 时保留细分，只对应 1 个时归约到 X。多主体罗列是噪声。
- **SafetyEvent**：`涉事主体-事件内容(选填)-事件类型`，主体不限于药品；事件类型 7 种：不良反应、不良事件、安全警示、黑框警告、说明书修订、风险提示、上市后监测。内容段源文没写就不写。召回/撤市归 RecallEvent；监督检查、抽检不合格、整改是噪声；没有主体的泛称是噪声。
- **RecallEvent**：优先用召回编号（如 FDA `D-xxxx-xxxx`），没有时用 `主体 + 召回`。
- **ClinicalTrial**：有注册号最好；试验代号、申办方方案号、`A vs B` 式整句标题都是合格实体（只是命名不合规，补别名，不降为噪声）；`临床试验`、`一项III期研究`、`Trial-Indication` 这类泛称和字段拼接是噪声。
- **事件后缀分流**：`-注销/-批准文号/-批准` → ApprovalEvent；不良反应等 7 种 → SafetyEvent；`-召回/-撤市` → RecallEvent；`-飞行检查/-不合格/-整改` 和 `-公告/-通告/-通知/-名单/-通报`（文档标题切片）→ 噪声。
- **一律不抽**：泛称类别名、文献元数据、文档标题、字段名拼接、受理号/批准文号（试验注册号不算）、与医药无关的实体、辅料溶媒。能唯一指代一个具体东西的是实体，只是流水号或字段值的是噪声。
- **命名**：禁止「该药」「这家公司」这类模糊名；Drug/Target/Indication/Pathway 必填 `name_en`，中英名互作别名；剂型后缀（片、胶囊）要规范，复方不拆。

**PrimeKG 锚点**：库里导入了 PrimeKG 的 4 类节点约 5.5 万个（Drug 来自 DrugBank、Indication 来自 MONDO、Target 来自 NCBI Gene、Pathway 来自 Reactome），`canonical_source='primekg'`、`is_verified=true`，只导了节点，没导关系边。监管文档里没有这些外部 ID，抽出来的实体只能靠名字规范化 + 语义对齐连到它们；目前对齐率还是 0，`is_verified=true` 实际上等于「来自 PrimeKG」。
